## 1. 插件逻辑入口文件位置

### 1.1 核心框架层（Cordis）

Cordis 是整个插件系统的基石，位于 `vendor/cordis/src/`。

| 文件 | 职责 | 关键导出 |
|------|------|----------|
| `vendor/cordis/src/index.ts` | 框架总入口，barrel export | 导出所有子模块 |
| `vendor/cordis/src/context.ts` | **DI 上下文**，基于 Proxy 的服务容器 | `Context` 类：`extend()`/`isolate()`/`intercept()` |
| `vendor/cordis/src/registry.ts` | **插件注册表**，管理插件 runtime | `RegistryService`：`plugin()`/`inject()`/`delete()`；`Plugin` 命名空间（Function/Constructor/Object.apply）；`Inject` 装饰器 |
| `vendor/cordis/src/fiber.ts` | **Fiber 生命周期**，插件效果和状态机 | `Fiber`：PENDING→LOADING→ACTIVE→DISPOSED/UNLOADING/FAILED |
| `vendor/cordis/src/service.ts` | **Service 基类**，所有命名服务的父类 | `Service`：自动注册到 `ctx.reflect.provide()` |
| `vendor/cordis/src/reflect.ts` | **ReflectService**，Proxy trap 实现服务解析 | `provide()`/`set()`/`get()`/`accessor()`/`notify()` |
| `vendor/cordis/src/events.ts` | **EventsService**，事件总线 | emit/waterfall/parallel/serial/bail 五种分发模式 |
| `vendor/cordis/src/logger.ts` | LoggerService，日志服务 | 分级日志 |

**核心设计**：`Context` 通过 `Proxy` 拦截属性访问，当读取 `ctx.xxx` 时自动通过 `ReflectService` 解析对应的服务实例。服务通过 `provide` 注册，通过 `inject` 声明依赖。

### 1.2 插件加载层（Loader）

Loader 位于 `vendor/loader/src/`，负责将 YAML 配置树转化为运行时插件实例。

| 文件 | 职责 | 关键导出 |
|------|------|----------|
| `vendor/loader/src/index.ts` | **Loader 服务入口**，继承 EntryTree | `Loader`：管理配置树、处理 `internal/config`/`internal/update`/`internal/plugin` 事件 |
| `vendor/loader/src/config/entry.ts` | **Entry 类**，单个插件配置节点 | `Entry`：import→init→update→dispose 完整生命周期 |
| `vendor/loader/src/config/tree.ts` | **EntryTree 抽象类**，条目树基类 | `EntryTree`：CRUD（create/remove/update/resolve）、import、await |
| `vendor/loader/src/config/group.ts` | **EntryGroup**，子条目容器；**Group 插件** | `EntryGroup`：批量创建/移除/更新；`Group`：嵌套 loader 条目组 |
| `vendor/loader/src/config/isolate.ts` | **Realm 隔离**，服务级作用域 | `Realm`/`LocalRealm`/`GlobalRealm`：通过事件钩子实现隔离切换 |
| `vendor/loader/src/config/utils.ts` | **JS 表达式求值**，配置插值 | `evaluate()`/`interpolate()`：YAML `!js` 表达式处理 |
| `vendor/loader/src/internal.ts` | **ModuleLoader 包装**，Node ESM 加载器适配 | `ModuleLoader`：v1/v2 两种 Node 模块加载器形态 |

**核心设计**：每个插件对应一个 `Entry` 实例，Entry 管理该插件从模块导入到 fiber 挂载的完整生命周期。`EntryTree` 以树形结构组织所有 Entry，支持嵌套子树。

### 1.3 应用启动层（Boot）

| 文件 | 职责 | 关键导出 |
|------|------|----------|
| `packages/boot/app-boot/src/index.ts` | **应用启动胶水层**（~600 行） | `boot()`：创建 Context→挂载 Loader→应用 patch→等待稳定 |
| `packages/boot/app-boot/src/profile.ts` | Profile 加载与组合 | `loadProfile()`/`composeEntries()`/`initProfile()` |
| `packages/boot/cmdline/src/index.ts` | 命令行参数解析 | `parseCmdline()`/`provideCmdline()` |

**`boot()` 函数是整个运行时启动的核心**：创建根 Context → 实例化 Loader → 应用 patch 层 → 等待所有 fiber settle → 返回稳定的 Context。

### 1.4 CLI 入口层

| 文件 | 职责 | 关键导出 |
|------|------|----------|
| `apps/cli/src/bin.ts` | **命令行主入口** | 分派三种模式：`profile`/`plugin`/`dump-config` |
| `apps/cli/src/plugin.ts` | **插件管理 CLI** | `runPlugin()`：pnpm 转发 + `reconcilePlugins()` 自动同步 bundle 列表 |
| `apps/cli/src/profile-boot.ts` | **Profile 启动序列**（~320 行） | `runProfile()`：composeProfile → boot() → HMR → appReady |

**启动流程**：`bin.ts` → `parseDshArgs()` → `runProfile()` → `composeProfile()`（加载 profile + 组合 patch 层）→ `boot()` → 安装 HMR → `appReady.commit()`

### 1.5 Bundle 组合层

Bundle 定义不同运行场景的插件组合，位于 `packages/bundle/`。

| Bundle | 包名 | 用途 | 核心依赖数 |
|--------|------|------|-----------|
| `packages/bundle/base/` | `@deepseek-ai/dsh-base` | 基础 bundle，所有场景的底座 | ~90+ 核心插件 |
| `packages/bundle/web-app/` | `@deepseek-ai/dsh-web-app` | 浏览器表面：前端 UI + Web 服务器 | ~80+ 插件（含 base 依赖） |
| `packages/bundle/sdk-minimal/` | `@deepseek-ai/dsh-sdk-minimal` | 最小 SDK：JSON-RPC + DeepSeek 适配器 | ~30+ 插件 |
| `packages/bundle/sdk-app/` | `@deepseek-ai/dsh-sdk-app` | SDK 应用：stdio JSON-RPC + 进程生命周期 | cmdline + jsonrpc-server |
| `packages/bundle/acp-app/` | `@deepseek-ai/dsh-acp-app` | ACP 自动化：纯 JSON-RPC stdio | acp + cmdline |
| `packages/bundle/headless/` | `@deepseek-ai/dsh-headless` | 无头运行：一次性 Agent 执行 | brand + cmdline + worker-thread |

每个 Bundle 通过 `package.json` 的 `dependencies` 声明包含哪些插件，通过 `dsh.bundle.patch` 指向 `cordis.patch.yml` 提供配置覆盖。

### 1.6 热更新层（HMR）

| 文件 | 职责 | 关键导出 |
|------|------|----------|
| `vendor/hmr/src/index.ts` | **HMR 服务**（~600 行） | `Hmr`：chokidar 监控 → 变更分析 → 缓存清除 → 重新导入 → 重新加载 |

**HMR 工作流程**：
1. chokidar 监控配置的 root 目录
2. 文件变更时分类：external（全量重载）/ config（配置刷新）/ module（部分重载）
3. 部分重载：分析依赖图 → 确定 accepted/declined 文件 → 清除 ESM loadCache + CJS Module._cache → 重新 import → 替换 fiber

### 1.7 宿主端服务层

| 文件 | 职责 | 关键导出 |
|------|------|----------|
| `packages/host/plugin-inventory/src/index.ts` | **插件清单网关** | `PluginInventoryGateway`：通过 `@Remote('list')` 暴露 Loader 条目快照 |
| `packages/core/agent/src/index.ts` | **AgentRegistry 服务** | `AgentRegistry`：`setFactory()`/`create()`/`resume()`/`register()` |
| `packages/core/session/src/index.ts` | **Session 管理** | `Session`/`SessionStore`：事件溯源式会话日志 |
| `packages/skill/skill/src/index.ts` | **SkillRegistry 服务** | `SkillRegistry`：provider catalogs + 分层 skill 解析 |

## 2. 逻辑实现精要

### 2.1 插件的三种形态

Cordis 支持三种插件定义方式：

```typescript
// 形态 1：函数插件（最常用）
function myPlugin(ctx: Context, config: MyConfig) {
  // 插件逻辑
}

// 形态 2：类插件
class MyPlugin {
  constructor(ctx: Context, config: MyConfig) {}
  apply(ctx: Context, config: MyConfig) {}
}

// 形态 3：对象插件
const myPlugin = {
  name: 'my-plugin',
  apply(ctx: Context, config: MyConfig) {}
}
```

所有形态都通过 `RegistryService.plugin()` 统一处理。注册表以 callback 函数作为 identity key，确保同一插件不会重复注册。

### 2.2 依赖注入与服务解析

**服务注册**：通过 `Service` 子类或 `provide` 声明

```typescript
// 方式 1：继承 Service
class MyService extends Service {
  constructor(ctx: Context) {
    super(ctx, 'myService')  // 注册为 ctx.myService
  }
}

// 方式 2：通过 provide 声明
myPlugin.provide = ['myService']
```

**服务注入**：插件通过 `inject` 声明依赖

```typescript
// 方式 1：数组形式（声明依赖，不关心配置）
myPlugin.inject = ['tools', 'llm', 'loader']

// 方式 2：Map 形式（声明依赖 + 服务配置）
myPlugin.inject = {
  tools: { strict: true },
  llm: undefined
}

// 方式 3：装饰器
@Inject('tools')
@Inject('llm')
class MyPlugin { ... }
```

**Proxy 解析**：当插件访问 `ctx.tools` 时，`ReflectService` 的 `get` trap 拦截属性访问，查找已注册的服务实例。如果服务尚未就绪，fiber 进入 `waiting` 状态，服务出现时自动激活。

### 2.3 插件生命周期状态机

```
PENDING → LOADING → ACTIVE → UNLOADING → DISPOSED
                    ↓
                  FAILED
```

| 状态 | 含义 |
|------|------|
| PENDING | 已创建 fiber，等待启动 |
| LOADING | 正在执行 apply() 或初始化 |
| ACTIVE | 插件正常运行 |
| FAILED | 初始化失败 |
| UNLOADING | 正在卸载（dispose 调用后） |
| DISPOSED | 已完全清理 |

**Fiber 的核心能力**：
- `effect()`：注册可逆效应（cleanup 自动调用）
- `dispose()`：递归清理所有注册的效应、监听器、子 fiber
- `update()`：配置变更时热更新
- `await()`：等待 fiber 到达终态

### 2.4 配置驱动的加载流程

```
1. CLI 启动 → parseDshArgs()
2. runProfile() → composeProfile()
   ├── loadProfile() — 加载 profile 目录
   ├── 读取 bundle 依赖 → 收集 bundlePatches
   ├── 加载 profile.patches（cordis.patch.yml）
   ├── 加载 homePatches（~/.dsh/cordis.patch.yml）
   └── 加载 overlays（--patch 参数）
3. boot(rootConfig, allPatches)
   ├── new Context() — 创建根上下文
   ├── ctx.plugin(Loader) — 挂载 Loader 服务
   ├── ctx.plugin(Include) — 挂载配置包含
   └── EntryTree 遍历配置条目
       ├── import(name) — 动态导入插件模块
       ├── ctx.registry.plugin(callback, config) — 注册到 Cordis
       └── fiber.await() — 等待插件 settle
4. 所有 fiber 稳定 → 返回 ctx
```

**关键代码位置**：
- 启动入口：`apps/cli/src/profile-boot.ts` → `runProfile()`
- 核心引导：`packages/boot/app-boot/src/index.ts` → `boot()`
- 条目挂载：`vendor/loader/src/config/entry.ts` → `Entry.init()` → `_init()` → `_start()`

### 2.5 配置分层合成

配置按以下优先级从低到高合成：

```
1. Bundle 层（package.json dependencies 中的插件默认配置）
   ↓ 按 dsh.profile.bundles 顺序应用
2. Profile 用户层（profile 目录下的 cordis.patch.yml）
   ↓
3. Home 用户层（~/.dsh/cordis.patch.yml，机器级偏好）
   ↓
4. Overlay 层（--patch 参数传入的配置）
   ↓
5. Telemetry 开关（DSH_TELEMETRY_DISABLED 环境变量）
```

**合成规则**：
- patch 按 `id` 命中时**整体替换** `config`，没有深合并
- 使用 `composeEntries()` 去重（后出现的同 id 条目覆盖先出现的）
- `structuredClone` 确保每次合成都是独立副本，防止引用污染

**配置文件格式**（`cordis.patch.yml`）：

```yaml
- id: compaction-basic          # 插件标识，对应 EntryOptions.id
  name: @deepseek-ai/dsh-xxx   # 可选：覆盖模块名
  config:                       # 传递给 apply(ctx, config) 的配置
    maxTokens: 64000
    thresholdRatio: 0.6
    retainRatio: 0.15
  disabled: false               # 可选：禁用插件
  inject:                       # 可选：覆盖依赖声明
    - tools
    - llm
```

支持 `!!js` 表达式注入环境变量：
```yaml
- id: my-plugin
  config:
    apiKey: !!js process.env.MY_API_KEY
```

### 2.6 热更新机制

**两层热更新**：

1. **配置热更新**（Loader 层）：`cordis.patch.yml` 变更时，Loader 重新合成配置树，对变更的条目执行 update/dispose/create
2. **模块热更新**（HMR 层）：源码变更时，清除 Node ESM/CJS 模块缓存，重新 import 插件模块，替换 fiber

**HMR 变更分类**：
- **External 变更**：框架自身代码变更 → 全量重启（`loader.exit()`）
- **Config 变更**：loader config 文件变更 → 刷新 include
- **Module 变更**：插件模块变更 → 部分重载（清除缓存→重新 import→替换 fiber）

### 2.7 事件系统与扩展点

Cordis 事件系统支持 5 种分发模式：

| 模式 | 用途 | 特点 |
|------|------|------|
| `emit` | 广播通知 | 无返回值，所有监听器并行执行 |
| `waterfall` | 管道/中间件 | 前一个监听器的返回值传给下一个，可短路 |
| `parallel` | 并行执行 | 所有监听器并行，等待全部完成 |
| `serial` | 串行执行 | 依次执行，支持 async |
| `bail` | 熔断 | 第一个非空返回值终止链路 |

**关键事件域**：

```typescript
// 工具执行管道
ctx.on('tools/pre-execute', handler)   // 拦截：可 deny/allow
ctx.on('tools/execute', handler)        // 包装：超时/重试/指标
ctx.on('tools/post-execute', handler)   // 后处理：结果转换

// Agent 生命周期
ctx.on('agent/pre-step', handler)       // 步骤前拦截
ctx.on('agent/request', handler)        // LLM 请求拦截
ctx.on('agent/request-error', handler)  // 错误处理

// 会话事件
ctx.on('session/created', handler)      // 会话创建
ctx.on('session/event', handler)        // 会话事件广播
ctx.on('session/flush', handler)        // 会话刷新

// 文件系统
ctx.on('fs/observed', handler)          // 文件变化
ctx.on('fs/write-intent', handler)      // 写入拦截
ctx.on('fs/edit-intent', handler)       // 编辑拦截

// Loader 生命周期
ctx.on('loader/entry-init', handler)    // 条目初始化
ctx.on('loader/partial-dispose', handler) // 部分销毁
ctx.on('loader/patch-context', handler)  // 上下文补丁
```

### 2.8 工具执行管道

```
模型消息 → tool/call
  → presentCall()                    # 生成待处理卡片
  → tools/pre-execute                # 拦截（权限/策略检查）
  → 单调守卫（tools.guard()）         # 不可撤销的拒绝
  → tools/execute                    # 执行包装（超时/重试/指标）
  → 工具 execute()                   # 实际执行
  → tools/post-execute               # 后处理（结果转换）
  → tools/result                     # 结果标准化
  → presentResult()                  # 生成完成卡片
```

**工具注册方式**：

```typescript
ctx.tools.register({
  name: 'my_tool',
  description: '工具描述',
  parameters: {
    input: { type: 'string', required: true }
  },
  output: {
    schema: { type: 'string' },
    render: (args, value) => [{ type: 'text', text: value }]
  },
  async execute(args, exec) {
    return '结果'
  }
})
```

### 2.9 作用域隔离

Loader 通过 Realm 机制实现插件间的服务隔离：

- **GlobalRealm**：全局共享服务（如 `loader`、`timer`）
- **LocalRealm**：本地隔离服务（每个 Realm 有独立的 symbol namespace）
- **默认隔离**：每个 Entry 通过 `ctx.extend()` 创建子上下文，自然隔离

隔离通过 `loader/entry-init`、`loader/patch-context`、`loader/partial-dispose` 三个事件钩子在条目生命周期中自动切换。

## 3. 如何实现自己的插件

### 3.1 最小插件模板

一个最简单的 Cordis 插件：

```typescript
// my-plugin/src/index.ts
import type { Context } from '@deepseek-ai/cordis'

/**
 * 我的第一个 DSH 插件
 * @param ctx - Cordis 上下文，提供服务访问
 * @param config - 配置对象，来自 cordis.patch.yml
 */
export default function myPlugin(ctx: Context, config: { message?: string }) {
  const message = config.message ?? 'Hello from my plugin!'
  ctx.logger.info(message)

  // 返回清理函数（可选）
  return () => {
    ctx.logger.info('my-plugin disposed')
  }
}
```

### 3.2 插件依赖声明

通过 `inject` 声明插件所需的已注册服务：

```typescript
// 函数形态
export const inject = ['tools', 'llm', 'loader']

// 类形态
export class MyPlugin {
  static inject = ['tools', 'llm']
  // ...
}

// 或使用装饰器
import { Inject } from '@deepseek-ai/cordis'

@Inject('tools')
@Inject('llm')
export class MyPlugin { ... }
```

可用的内置服务名称：

| 服务名 | 来源包 | 用途 |
|--------|--------|------|
| `tools` | dsh-tools | 工具注册表和执行管道 |
| `llm` | dsh-llm | LLM 适配器注册表 |
| `loader` | cordis-plugin-loader | 插件配置树管理 |
| `agents` | dsh-agent | Agent 注册表 |
| `session` | dsh-session | 会话存储 |
| `fs` | dsh-fs-local | 文件系统提供者 |
| `sandbox` | dsh-sandbox-local | 进程沙箱 |
| `shell` | dsh-shell-env | Shell 执行器 |
| `hmr` | cordis-plugin-hmr | 热模块替换 |
| `timer` | cordis-plugin-timer | 定时器服务 |
| `settings` | dsh-settings-file | 用户设置存储 |
| `subagents` | dsh-subagent | 子代理提供者 |
| `agentTeams` | agent-team | 多代理协作 |

### 3.3 注册工具

工具是插件最常见的扩展方式，让模型可以调用自定义功能：

```typescript
import type { Context } from '@deepseek-ai/cordis'

export default function myToolPlugin(ctx: Context) {
  // 注册一个工具
  const disposable = ctx.tools.register({
    name: 'calculate',
    description: '执行数学计算',
    parameters: {
      expression: {
        type: 'string',
        description: '要计算的数学表达式',
        required: true,
      },
    },
    output: {
      schema: { type: 'number' },
      render: (args, result) => [{
        type: 'text',
        text: `计算结果: ${result}`,
      }],
    },
    async execute(args, exec) {
      // args.expression 是用户传入的表达式
      const result = Function(`"use strict"; return (${args.expression})`)()
      return result
    },
  })

  // 返回清理函数，工具会被自动注销
  return () => disposable()
}
```

### 3.4 监听事件

通过事件系统与系统其他部分交互：

```typescript
import type { Context } from '@deepseek-ai/cordis'

export default function myEventPlugin(ctx: Context) {
  // 监听文件变化（emit 模式）
  ctx.on('fs/observed', (event) => {
    ctx.logger.info(`文件变化: ${event.path}`)
  })

  // 拦截工具执行（waterfall 模式，可短路）
  ctx.on('tools/pre-execute', async (exec, next) => {
    if (exec.tool === 'dangerous_tool') {
      return { kind: 'deny', reason: '此工具已被禁用' }
    }
    return next()  // 继续执行链
  })

  // 监听 Agent 步骤（waterfall 模式）
  ctx.on('agent/pre-step', async (step, next) => {
    ctx.logger.info(`Agent 即将执行步骤`)
    return next()
  })

  // 使用 effect 注册可逆监听器（自动清理）
  ctx.effect(() => {
    const handler = (event: any) => { /* ... */ }
    ctx.on('session/event', handler)
    return () => {
      // cleanup：effect 释放时自动调用
    }
  })
}
```

### 3.6 注册服务

创建可被其他插件使用的服务：

```typescript
import { Service } from '@deepseek-ai/cordis'
import type { Context } from '@deepseek-ai/cordis'

// 定义服务
class MyService extends Service {
  static inject = ['loader']  // 声明依赖

  private data = new Map<string, any>()

  constructor(ctx: Context) {
    super(ctx, 'myService')  // 注册为 ctx.myService
  }

  // Service.init 生成器：管理服务生命周期
  async* [Service.init]() {
    this.ctx.logger.info('MyService 启动')
    yield () => {
      this.ctx.logger.info('MyService 清理')
    }
    // 初始化逻辑...
  }

  set(key: string, value: any) {
    this.data.set(key, value)
  }

  get(key: string) {
    return this.data.get(key)
  }
}

// 插件挂载服务
export default function myServicePlugin(ctx: Context) {
  ctx.plugin(MyService)
  // 现在其他插件可以通过 ctx.myService 访问
}
```

### 3.7 生命周期管理

使用 `ctx.effect()` 确保资源被正确清理：

```typescript
import { FiberState } from '@deepseek-ai/cordis'

export default function myLifecyclePlugin(ctx: Context) {
  // effect 会在 fiber dispose 时自动调用清理函数
  ctx.effect(() => {
    const interval = setInterval(() => {
      ctx.logger.info('心跳')
    }, 30000)

    // 清理函数
    return () => {
      clearInterval(interval)
    }
  })

  // 生成器形式：支持多个清理步骤，按逆序执行
  ctx.effect(function* () {
    const resource1 = acquireResource1()
    yield () => releaseResource1(resource1)

    const resource2 = acquireResource2()
    yield () => releaseResource2(resource2)
    // 释放顺序：resource2 → resource1
  })

  // 监听 fiber 状态变化
  ctx.on('internal/status', (fiber) => {
    if (fiber.state === FiberState.UNLOADING) {
      ctx.logger.info('插件正在卸载')
    }
  })
}
```

### 3.10 完整示例：自定义 LLM 适配器插件

```typescript
// my-llm-adapter/src/index.ts
import { z } from '@deepseek-ai/schemastery'
import type { Context } from '@deepseek-ai/cordis'

// 配置 schema
const Config = z.object({
  apiKey: z.string().required(),
  baseUrl: z.string().default('https://api.example.com'),
  model: z.string().default('my-model'),
  temperature: z.number().min(0).max(2).default(0.7),
})

// 插件元信息
export const name = 'my-llm-adapter'
export const inject = ['llm']  // 依赖 LLM 注册表
export { Config }

// 插件入口
export default function apply(ctx: Context, config: z.infer<typeof Config>) {
  ctx.logger.info(`注册 LLM 适配器: ${config.baseUrl}`)

  // 注册 LLM 适配器
  const disposable = ctx.llm.registerAdapter(['my-provider'], {
    async complete(request) {
      const response = await fetch(`${config.baseUrl}/v1/chat/completions`, {
        method: 'POST',
        headers: {
          'Content-Type': 'application/json',
          'Authorization': `Bearer ${config.apiKey}`,
        },
        body: JSON.stringify({
          model: config.model,
          messages: request.messages,
          temperature: config.temperature,
        }),
      })
      return response.json()
    },
  })

  // 清理
  return () => disposable()
}
```

对应的 `cordis.patch.yml` 配置：

```yaml
- id: my-llm-adapter
  config:
    apiKey: !!js process.env.MY_API_KEY
    baseUrl: https://api.my-provider.com
    model: my-custom-model
    temperature: 0.8
```

## 附录：关键技术参考

### Cordis 核心 API

| API | 用途 |
|-----|------|
| `ctx.plugin(Plugin, config?)` | 注册插件 |
| `ctx.effect(fn)` | 注册可逆效应 |
| `ctx.on(event, handler)` | 监听事件 |
| `ctx.emit(event, ...args)` | 发射事件 |
| `ctx.extend(meta)` | 创建子上下文 |
| `ctx.isolate(name)` | 创建隔离上下文 |
| `ctx.get(serviceName)` | 获取服务实例 |
| `ctx.inject(deps, callback)` | 依赖注入回调 |

### Loader 核心 API

| API | 用途 |
|-----|------|
| `ctx.loader.create(options)` | 动态创建插件条目 |
| `ctx.loader.remove(id)` | 移除插件条目 |
| `ctx.loader.update(id, options)` | 更新插件条目 |
| `ctx.loader.resolve(id)` | 解析插件条目 |

### 事件分发模式选择指南

| 场景 | 推荐模式 | 原因 |
|------|----------|------|
| 广播通知 | emit | 无需返回值，所有监听器并行 |
| 管道/中间件 | waterfall | 需要链式传递和短路能力 |
| 并行等待 | parallel | 需要等待所有监听器完成 |
| 顺序处理 | serial | 需要保证执行顺序 |
| 单一匹配 | bail | 找到第一个匹配即停止 |
