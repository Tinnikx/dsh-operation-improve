# 023 多选高亮在纹理主题上的可辨性

- 目标：批量圈选时，**在第三方主题把侧栏渲染成纹理/壁纸的现场**也能一眼看出哪些行被选中。这是观感问题，不是判据问题——判据侧的口径已由[交接 022](./022-multiselect-contrast-baseline.md) 定完。
- 范围：[src/row-states/index.js](../../src/row-states/index.js) 的 `[role="treeitem"][data-dsh-oi-selected]` 段（描边配方与填充配方），加上「纹理底上怎么算可辨」的判据口径。行为（选择集、右键菜单、多选规则本身）不在范围里。
- 状态：**未开始**。要动的是用户可见的观感，动手前需要先定形状。

## 现象（实测，harness 0.2.1-alpha.1，副本带 `dsh-any-background` 0.3.6）

那份主题把侧栏底钉成 `hsla(40,34%,31%,0.49)` 并叠了模糊纹理。纹理意味着**「侧栏底色」在这里不是一个颜色**：

- 同一条多选行内部，相邻采样点的红通道从 97 跳到 140（截图 4 倍出图，165 个采样点）。
- 按 16 级量化分桶后，主导桶只占多选行 49% 的采样点、对照行 58%——`verify:row-states` 的平色守卫因此把那两档的 6 条可辨性判据整组 SKIP（另加 2 条同源），退出码 1。
- 描边本身没问题：截图像素 `rgb(137,170,254)` 与 `box-shadow` 解析值逐字相同。它的问题在于**局部**——对行内主导底 `rgb(81,68,44)` 是 4.18，对亮纹处的 `rgb(140,116,69)` 只剩 1.97。同一条线，行里有的段看得见、有的段看不见。
- 行内填充在纹理底上的净效果是色相偏一点、亮度几乎不变（多选行均值 `rgb(105,106,104)` 对对照行均值 `rgb(120,100,80)`），肉眼看就是「底色没动」。

## 约束与已排除的走法

- **CSS 挑不了「按底色亮度」的描边**：没有亮度比较函数，`color-mix()` 与 `light-dark()` 都不看色值大小，能挑的只有属性档；而那份主题恒把 `data-ds-dark-theme` 挂着（实测摘掉后每帧写回），属性档等于只有一档。
- **一枚固定实色描边不可能在所有底色上过 3:1**：棕色底（亮度 0.061~0.126）要过 3:1，描边亮度得 ≥0.478 或 ≤0.0037，也就是接近纯白或接近纯黑；同一枚纯黑描边在标准深色侧栏（亮度 0.011）上只有 1.03，直接消失。019 的配方（强调色 70% 混 `--dsw-alias-label-primary`）在标准主题上成立，是因为文字色跟档位走；那份主题把文字色钉成 `#fff`，描边就永远压不暗。

## 三条候选形状

对比度只看相对亮度，所以「按亮度扫一遍 0~1」就等价于遍历**所有实色底**（色相进不了这个比值）。下表是这么扫出来的：**这一形状在最坏底上，至少有一枚色环与底的对比度**（`srgb` 那列是最坏底的通道亮度）：

| 形状 | 最坏底保证 | 最坏底 srgb 亮度 |
| --- | --- | --- |
| 单环，今天的深档描边 `rgb(137,170,254)` | 1.00 | 0.674 |
| 单环，今天的浅档描边 `rgb(122,159,237)` | 1.00 | 0.627 |
| 双环，强调色 + 纯黑 | 2.50 | 0.303 |
| 双环，深档描边 + 纯黑 | 3.04 | 0.353 |
| 双环，纯黑 + 纯白 | 4.58 | 0.460 |

1. **相邻双环**（推荐先试）：外 1px 强调色、内 1px 一枚中性极色垫圈，思路与 WCAG 2.2 焦点环一致——一枚与底融了，另一枚还站着。上表说明「加黑垫圈」刚好压过 3:1（3.04），换成黑+白最稳（4.58）但丢掉「蓝=选中」的语义。零运行时成本，代价是观感要重新验收，而 32px 的行里 2px 环已经很显眼。
2. **运行时按实测底色算描边**：像 022 那样采一片像素、取主导桶与两端分位，把描边写成 CSS 变量。能真的贴底调色，但功能 10 现在是**纯样式表**（`src/row-states/index.js` 只有 CSS，由 client 入口统一插入），加 JS 等于改这个功能的形态；那份主题每帧重画变量，还得 debounce。
3. **换承重通道**：整圈 1px 描边换成行内更粗的面积信号（左侧色块加宽、或行首图标位），不靠细线跟纹理抢对比度。改动最小，但要重新定义「选中集」的视觉语法，与功能 10 的当前会话竖条会撞车。

## 需要先定的三件事

1. 形状选 1 / 2 / 3 哪一条（1 是唯一不改功能形态的走法）。
2. 判据怎么在纹理现场成立：像素对比度在这种底上不是一个数。候选口径是「取行内主导桶与 p10/p90 两端各自算对比度，要求**最差端**过阈值」——把「有的段看不见」变成可判定的东西。没定之前，这套件在第三方现场就停在 9 条 SKIP 上。
3. 覆盖哪个行型：现在三条可辨性判据量的是「选中 + 多选」叠加态，**未选中 + 多选**（批量圈选里除当前会话外的每一行）没有判据。按形状定完要一起补。

## 验证

改完的验收方式（八套串行 + 两种现场，与 022 同一条路）：

```
PATH=$HOME/.nvm/versions/node/v24.14.0/bin:$PATH npm run stack:up
PATH=$HOME/.nvm/versions/node/v24.14.0/bin:$PATH npm run verify:row-states        # 标准现场必须全绿
DSH_OI_KEEP_THEME_PLUGIN=1 npm run stack:up && npm run verify:row-states         # 第三方现场按新口径判定，不再整组 SKIP
```

外加观感验收：纹理现场截一张多选行的图（截图这条链在 022 里已经打通），由用户目测确认「哪几行被选中看得出来」。019 那轮的教训仍然有效——computed 值与对比度数字替代不了眼睛。

## 未验证

- 真桌面 Electron 客户端上的多选观感从没测过（八套 live 全打 web 测试栈）。
- 那份主题把 `schemeOverride` 设成 `light` 时钉法是否一样，没测。
- 双环的 4.58 只是亮度公式上的算术结论，没有渲染读数，也没做过观感验收。
- 纹理现场的局部极值取样只跑了一次（同一行 165 个点里的 97 与 140），样本量小，换一条会话行、换个滚动位置没重采。
